# Local CORE Guide end-to-end preview

This development preview connects the existing hallway guide UI to the Worker-compatible handler
over real localhost HTTP. It is not a production backend. Every knowledge record is synthetic and
the provider response is generated by an injected deterministic fetch double.

## Safety boundary

- The browser feature is enabled only when Vite replaces `import.meta.env.DEV` with `true` **and**
  the URL contains both `guideMock=1` and `guideBackend=local`.
- The shim binds only to `127.0.0.1:4188` and permits the explicitly configured Vite origin
  `http://127.0.0.1:4179`.
- Browser requests can target only `http://127.0.0.1:4188/guide`.
- The OpenAI adapter receives `createFakeOpenAIFetch()` explicitly. It never receives global
  `fetch`, reads no environment variables, and has no fallback transport.
- The fake credential is a literal non-secret fixture value. No real key is accepted or needed.
- Questions, answers, and transcripts are not logged or persisted. Temporary memory contains only
  bounded canonical topic, specialist, and destination IDs and is cleared on dialogue close.
- This work does not create a Worker project, cloud route, database, deployment, or billable call.

## Request flow

```text
existing hallway-guide + Dialogue
  -> browser request/response validation
  -> POST http://127.0.0.1:4188/guide
  -> Node Request/Response bridge
  -> existing Worker handler validation
  -> approved-only fictional knowledge loader
  -> Stage 2/3 deterministic retrieval and temporary context
  -> existing OpenAI Responses adapter
  -> injected fake Responses transport
  -> Worker grounding, citation, route, and response validation
  -> browser validation and existing Dialogue UI
```

The fake provider returns only answer text, the selected topic, and allowed fact IDs. The Worker
reconstructs citations, specialist IDs, destination IDs, and canonical directions from its
server-owned approved fixture. Unsupported questions bypass the provider. Provider errors,
refusals, timeouts, malformed output, rate denial, and budget denial fail closed through the
existing validated unavailable response.

## Run locally in PowerShell

Open two PowerShell windows. In the first:

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd run guide:local
```

In the second:

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd run dev -- --host 127.0.0.1 --port 4179 --strictPort
```

Open normal scripted mode at `http://127.0.0.1:4179/`. Open the local backend preview at
`http://127.0.0.1:4179/?guideMock=1&guideBackend=local`.

The automatic welcome remains scripted. Close it, approach the existing CORE Guide, press `E`,
finish its scripted branch, and select **Ask a question**. Try:

- `How do folded machines move?`
- `Where can I find them?`
- `What do they specialize in?`
- `What is the weather tomorrow?` (safe unsupported fallback)

To simulate browser-visible backend failure, stop only the backend window with `Ctrl+C`, leave Vite
running, and submit another question. Restart `npm.cmd run guide:local` to restore it. Stop each
server with `Ctrl+C` in the PowerShell window where that server was launched.

## Tests

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd test
npm.cmd run build
```

The local E2E test binds the shim, makes a real loopback request, and closes it in `finally`. The
browser adapter tests cover validation, wrong request IDs, invalid JSON, connection failure,
superseding requests, abort, reset, and ID-only context. Worker and OpenAI adapter suites cover
unknown IDs, ambiguity, timeout, refusal, malformed output, rate denial, budget denial, prompt
injection, canonical routing, and logging privacy.

## Known local-preview limits

The authoritative fixture currently contains one approved supported topic (`folded-machines`) and
one specialist route. Draft, in-review, and retired topics intentionally remain unavailable, so a
second approved-topic context switch cannot be demonstrated without a separately reviewed fixture
version. Rate and budget controls are injected test interfaces, not durable distributed controls.
No NVDA claim is made; an actual NVDA session remains required.
