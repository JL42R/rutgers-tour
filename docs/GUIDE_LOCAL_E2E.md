# Local CORE Guide end-to-end preview

This development preview connects the existing hallway guide UI to the Worker-compatible handler
over real localhost HTTP. It is not a production backend. Every knowledge record is synthetic and
the provider response is generated by an injected deterministic fetch double.

## Safety boundary

- The browser feature is enabled only when Vite replaces `import.meta.env.DEV` with `true` **and**
  the URL contains both `guideMock=1` and `guideBackend=local`.
- The shim binds only to `127.0.0.1:4188` and permits the explicitly configured Vite origin
  `http://127.0.0.1:4179`.
- Browser requests can target only `http://127.0.0.1:4188/guide`.
- The optional `guideProfile` query parameter accepts only the fixed value `retrieval-quality`.
  It cannot name a file, path, URL, or arbitrary knowledge version.
- The OpenAI adapter receives `createFakeOpenAIFetch()` explicitly. It never receives global
  `fetch`, reads no environment variables, and has no fallback transport.
- The fake credential is a literal non-secret fixture value. No real key is accepted or needed.
- Questions, answers, and transcripts are not logged or persisted. Temporary memory contains only
  bounded canonical topic, specialist, and destination IDs and is cleared on dialogue close.
- This work does not create a Worker project, cloud route, database, deployment, or billable call.

## Request flow

```text
existing hallway-guide + Dialogue
  -> browser request/response validation
  -> POST http://127.0.0.1:4188/guide
  -> Node Request/Response bridge
  -> existing Worker handler validation
  -> approved-only fictional knowledge loader
  -> Stage 2/3 deterministic retrieval and temporary context
  -> existing OpenAI Responses adapter
  -> injected fake Responses transport
  -> Worker grounding, citation, route, and response validation
  -> browser validation and existing Dialogue UI
```

The local browser uses API schema v1.1 so approved friendly specialist and destination names cross
the Worker boundary. The handler still supports v1.0 callers and omits the v1.1-only name fields in
their responses.

The fake provider returns only answer text, the selected topic, and allowed fact IDs. The Worker
reconstructs citations, specialist IDs, destination IDs, and canonical directions from its
server-owned approved fixture. Unsupported questions bypass the provider. Provider errors,
refusals, timeouts, malformed output, rate denial, and budget denial fail closed through the
existing validated unavailable response.

In the advanced profile, the fake provider deliberately returns non-authoritative prose. The
Worker discards that prose and constructs the visitor answer from the selected approved facts, so
the browser never presents the fake provider wording as evidence.

## Run locally in PowerShell

Open two PowerShell windows. In the first:

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd run guide:local
```

In the second:

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd run dev -- --host 127.0.0.1 --port 4179 --strictPort
```

Open normal scripted mode at `http://127.0.0.1:4179/`. Open the local backend preview at
`http://127.0.0.1:4179/?guideMock=1&guideBackend=local`.

The automatic welcome remains scripted. Close it, approach the existing CORE Guide, press `E`,
finish its scripted branch, and select **Ask a question**. Try:

- `How do folded machines move?`
- `Where can I find them?`
- `What do they specialize in?`
- `Tell me about glass gardens.`
- `Where can I find that?`
- `What is the weather tomorrow?` (safe unsupported fallback)

### Advanced retrieval-quality profile

Use the same Vite command above. In the backend window, run:

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd run guide:local -- --profile retrieval-quality
```

Then open
`http://127.0.0.1:4179/?guideMock=1&guideBackend=local&guideProfile=retrieval-quality`.
This selects one fixed, reviewed synthetic profile on both sides of the localhost boundary. Try:

- `How do the origami contraptions rotate when I tug them?` (natural alias, two approved sources)
- `How do I get there?` (ID-only contextual follow-up)
- `Tell me about the prism greenhouse.` (synonym-driven topic switch)
- `What can you tell me about orbit rings?` (intentional ambiguity)
- `What color is the signal crystal?` (intentional approved-source conflict)
- `How fast do the automata move?` (unsupported specific claim)
- `What is the maximum safe speed of paper automata?` (same-topic unsupported property)
- `Where can I purchase a mirror-grove fruit token?` (unsupported lookalike relation)
- `Which colored tabs identify the repeating fold's reset points?` (property-aware grammar)

The last two questions must show the concise verified-answer fallback. They must not display an
unrelated fact, citation, specialist, destination, or directions, and they must not call the fake
provider. A relevant topic is not enough: the reviewed fact must cover the requested property.

Ordinary demonstrations must omit `--test-controls`. The automated Chrome lifecycle check alone
starts the backend with:

```powershell
npm.cmd run guide:local -- --profile retrieval-quality --test-controls
```

That flag exposes one fixed, POST-only localhost transition at
`/guide-test/advance-knowledge`. It accepts no document, path, metadata, or visitor content and can
only retire the preselected fictional cloud-kite records once. After the transition, a follow-up
that carries the retired IDs receives a friendly stale-context response and clears those IDs; the
next fresh approved question succeeds.

To simulate browser-visible backend failure, stop only the backend window with `Ctrl+C`, leave Vite
running, and submit another question. Restart `npm.cmd run guide:local` to restore it. Stop each
server with `Ctrl+C` in the PowerShell window where that server was launched.

## Tests

```powershell
Set-Location C:\dev\rutgers-tour-issue47-local-e2e
npm.cmd test
npm.cmd run build
```

The local E2E test binds the shim, makes real loopback requests for both approved topics, and closes
it in `finally`. The browser adapter tests cover validation, authoritative friendly names, wrong
request IDs, invalid JSON, connection failure, superseding requests, late responses, abort, reset,
ID-only context, and exact stale-context recovery. Worker and OpenAI adapter suites cover unknown
IDs, ambiguity, timeout, refusal, malformed output, rate denial, budget denial, prompt injection,
canonical routing, and logging privacy. The Chrome runner covers default success, the advanced
retrieval flow, backend-off failure, and production isolation. It uses physical Enter/Escape/Tab key
events and checks the live region and exact focus restoration; this is automated browser coverage,
not a manual NVDA claim.

## Known local-preview limits

The default fixture contains two approved synthetic topics (`folded-machines` and `glass-gardens`).
The allowlisted advanced profile adds the fixed retrieval-quality corpus only to the development
browser path; draft and retired records remain unavailable. Neither profile loads production CORE
facts. Rate and budget controls are injected test interfaces, not durable distributed controls. No
NVDA claim is made; an actual NVDA session remains required.

The 57-case profile evaluation and examined 20-/30-case diagnostics are documented in
`GUIDE_DOCUMENT_RETRIEVAL.md`. A prospectively frozen 44-case Codex-authored challenge improved
supported recall while retaining zero false support, but still passed only 30/44 complete Worker
outcomes. The deterministic policy remains over-conservative and is not production-ready.
Document ingestion and arbitrary publication remain outside the browser. The
fixed Chrome retirement control demonstrates version change and stale context only; it is not a
content-management endpoint.
